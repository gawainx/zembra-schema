# Supabase/Postgres 统一 Schema 契约需求澄清

## 需求理解

zembra-schema 必须成为本地 SQLite 与 Supabase/Postgres 远端同步协调层的唯一 schema source of truth。SQLite 与 Supabase/Postgres 可以使用不同数据库类型和平台能力，但必须共用同一个业务语义、同一个 schema version、同一条迁移演化路径。

backend 仓库只能消费 zembra-schema 发布的 schema 产物，不能独立维护 Postgres 业务 schema、独立定义远端字段语义，或使用独立于 zembra-schema 的 schema 版本体系。

## 已确认决策

- Supabase/Postgres 可以作为双向同步协调层，不限于只读备份。
- SQLite 与 Supabase/Postgres 必须共用同一个 schema version。
- `postgres/` 存放通用 Postgres DDL 和 migrations。
- `supabase/` 只存放 RLS、Realtime、policy 等 Supabase 平台专属配置。
- SQLite 与 Postgres migration 编号强绑定，同一编号代表同一业务版本。
- 当前阶段 RLS/Auth 不纳入统一 schema version，只保留平台配置说明。

## 仓库现状关联

当前仓库已经维护：

- `migrations/sqlite/current_schema.sql`：当前完整 SQLite DDL。
- `migrations/*.sql`：SQLite 迁移链。
- `json/*.schema.json`：对象级 JSON Schema 契约。
- `note_schema.md`：人读 schema 说明。
- `CHANGELOG.md`：schema 版本记录。

当前缺口：

- 缺少正式 Postgres DDL 和 Postgres migration 产物。
- `note_schema.md` 仍以本地数据库 schema 为主要表述。
- 部分 JSON Schema 未完全覆盖 `0.4.0` SQLite 当前 DDL 中的 workspace 与 sync 字段。
- backend 对 Supabase/Postgres 的消费边界还没有被 zembra-schema 文档明确约束。

## 范围确认

本轮纳入：

- 新增 Postgres/Supabase 契约目录结构。
- 新增 Postgres 当前完整 DDL。
- 新增与 SQLite 同编号的 Postgres migration。
- 新增 SQLite 空结构版本迁移，用于登记统一远端契约版本。
- 补齐 JSON Schema 中缺失的 workspace 与 sync 对象契约。
- 更新 `note_schema.md` 和 `CHANGELOG.md`，明确统一版本口径。

本轮不纳入：

- backend sync worker 或 backup worker 实现。
- Supabase 项目部署、环境变量和 CI 发布流程。
- RLS/Auth 策略的正式版本化。
- 附件二进制同步。
- UI 和冲突处理界面。

## 成功标准

- 仓库中存在正式 Postgres DDL 和 migration 产物。
- SQLite 与 Postgres 的最新 schema version 同为 `0.5.0`。
- JSON Schema 覆盖 workspace、sync change、sync state、sync conflict，以及业务对象的 workspace/sync 字段。
- 文档明确 backend 不能独立演化 Postgres 业务 schema。
- SQLite DDL、SQLite migration 链、JSON 文件和 Postgres SQL 语法检查通过。
